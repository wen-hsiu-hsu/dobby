> 慢的原因是呼叫模式（逐筆查、人為延遲），不是 Notion 本身或 rate limit。以下都**不是 bug**：結果正確，只是慢，不是急件，依效益排序。做完任何一項後，都要在 `/logs` 時間軸比對同類指令前後的 Notion 呼叫數與總耗時。

- [ ] **一次 Notion 寫入卡 43 秒，同一天的報名／請假全部連鎖逾時。**（2026-10-04 測試環境實測，本機 `logs/app.2026-10-04.1.log`）

    經過：同一人在群組快速連送兩輪 `+1`、`-1`、`假`、`銷假`，共 8 則，全部收到當時的逾時訊息「處理時間較長，這次操作可能已經完成，請勿重複操作」（現在的文案見 `with-fresh-calendar-event.ts:17`、`:20`）。
    - 起因是第一則 `+1`（reqId `a7d55c`，17:46:22）寫零打名單的 PATCH 花了 **43.2 秒**。這段時間沒有 429，也沒有重試，同時段其他 Notion 呼叫都在 0.4～0.5 秒。完全相同的 payload 在同一頁寫過十幾次都約 0.5 秒，所以不是「零打」多選欄位新增選項造成的，是 Notion 端偶發的慢回應。本機 log 共 1,378 次 Notion 呼叫：中位數 0.39 秒，p99 2.4 秒，超過 10 秒的只有 2 次，這次是最大值（9/29～10/4 超過 5 秒的共 3 次）。
    - **寫入其實早就生效，慢的是回應。** 回應 17:47:06 才到，但回應裡的 `last_edited_time` 是 `09:46`（UTC，精度到分鐘），表示寫入在回應前至少 7 秒就落地了。
    - 其餘 7 則都鎖在同一個 key（活動日期 `2026-10-10`），排在它後面，等滿 10 秒（`mutex.ts:9` 的 `TIMEOUT_MS`）就收到逾時訊息。第二輪（17:47:01～04）進來時第一輪還有 3 個任務在排隊，所以也各等了 11～13 秒（`waitMs` 11001～13443）。第二輪如果沒有這些積壓，4 個任務每個佔鎖 1.4～2.3 秒，不會逾時。
    - 背景寫入照 FIFO 全部完成，兩輪都是一加一減，最後狀態跟操作前一樣，資料正確。背景完成後送出的回覆全部 `Reply failed`（400），這是預期的，replyToken 已經被逾時訊息用掉了（[ADR 0002](adr/0002-mutex-timeout-does-not-cancel-task.md)）。

    **不是 bug**：mutex 照設計守住了資料正確性，逾時訊息也正確地叫使用者不要重試。觸發條件是 Notion 的罕見長尾，不是急件。

    這次也發現進鎖順序是「誰先查完」，不是「誰先送出」（第二輪送出 `+1 → -1 → 假 → 銷假`，進鎖卻是 `+1 → 假 → -1 → 銷假`）。2026-10-04 已用號碼牌閘門改成照收到順序進鎖（[ADR 0018](adr/0018-entry-gate-orders-lock-entry.md)），不在這項的範圍內了。

    **排隊中逾時的任務現在仍會執行。** 2026-10-04 曾改成取消排隊中就逾時的任務（回「這次操作沒有執行」），同一天又撤掉：取消會讓最早排隊的人最先被跳過，破壞先送先報（[ADR 0002](adr/0002-mutex-timeout-does-not-cancel-task.md)「例外」、ADR 0018）。2026-10-05 起改成讓結果可以查證（[ADR 0019](adr/0019-members-verify-timeout-via-next.md)）：逾時訊息依任務開始了沒分成「可能已完成」和「已排隊，會依序處理」兩種，都引導到開放給所有成員的 `@Dobby next`；還有任務沒跑完時，`next` 會另附「還有 N 筆正在處理」的提醒。下面的方向只能減輕，擋不住卡住的那一次寫入：

    各方向都有代價：
    - **縮短佔鎖時間**：2026-10-04 已把請假人姓名查詢和 LINE 回覆移到鎖外（`with-fresh-calendar-event.ts` 的 `replyStatus`），每次佔鎖少約 0.5～0.7 秒。能減少連鎖逾時波及的範圍，但擋不住第一個卡住的寫入。另外，背景完成後的那次 `Reply failed` 也不會再出現了：逾時後不會走到鎖外組卡片、回覆那步。
    - **拉長 mutex 逾時**：replyToken 約 1 分鐘內有效（`docs/architecture.md`「Fire-and-Forget Webhook 處理」），這次 8 則都在送出後 49 秒內完成，逾時改成約 50 秒的話，大家都會收到真正的結果。陷阱：使用者在群組裡可能乾等幾十秒沒有任何回應（LINE 的「輸入中」動畫只支援一對一聊天），比較容易重打；`+N` 不是冪等的，重打會重複報名，比現在的「請勿重複操作」更糟。要改的話，`TIMEOUT_MS` 是所有 key 共用的，`trackUser` 的鎖也會跟著變長。
    - **不要幫 Notion 請求加逾時中斷（AbortController），也不要重送或同時發兩個請求取最快的（hedging）**：Notion 沒有條件式寫入或冪等鍵，被中斷的 PATCH 可能稍後仍在 Notion 端生效（這次的 `last_edited_time` 顯示寫入確實早於回應落地）。這時排在後面的任務已經讀完、寫完，晚到的舊 PATCH 會把它蓋掉，造成真正的資料錯誤。只對 GET 加逾時是安全的，但這次卡住的是 PATCH，幫不上忙。
    - 觀察方式：`/logs` 搜尋 `Mutex task finished` 的 `callerTimedOut: true`（2026-10-04 短暫開過取消，那段期間的 `cancelled: true` 是排隊中被跳過、沒有執行的），以及 `Notion API response` 的 `durationMs` 超過 10000 的呼叫。

- [ ] **同一場活動 10 秒內大約只能處理 8～9 則報名／請假，搶報時排在後面的人就算 Notion 正常也會收到逾時訊息。**（2026-10-05 從本機 log 推算，尚未實測）

    現況：報名／請假都鎖活動日期（`with-fresh-calendar-event.ts:40`），每個任務在鎖內做一次 refetch（`calendarRepo.findByDate`）加一次 PATCH（`updateGuests` 或 `updateAbsentees`，`calendar-repository.ts:76`、`:84`）。2026-10-04 20:41 改成鎖外組卡片之後，本機 log 的佔鎖時間（`Mutex task finished` 的 `heldMs`，日期 key）n=18：中位數 1,066ms，最短 829ms，最長 2,992ms。逾時是 10 秒（`mutex.ts:9`），而且從呼叫 `withMutex` 起算、包含排隊時間，所以同一個 key 一次湧進 N 則時，第 N 則大約要等 (N−1)×1.07 秒才輪到。算下來大約第 9～10 則開始逾時，遇到長尾的話更早。

    **不是 bug**，資料不會錯：逾時的任務仍會依序寫入（[ADR 0002](adr/0002-mutex-timeout-does-not-cancel-task.md)），使用者會收到「已排隊，會依序處理」並被引導用 `@Dobby next` 確認（[ADR 0019](adr/0019-members-verify-timeout-via-next.md)）。但這比 43 秒那種 Notion 長尾更可能發生：只要週五開放報名時同一場有十人左右幾乎同時 `+1` 就會觸發。目前 log 幾乎都是測試流量（報名只有 2 個 userId），**還沒觀察過真正的搶報**，上面的上限是推算的。

    先確認再決定要不要做：
    - 看 Pi 上真實搶報時段的 `Mutex task finished`：`queuedAhead` 最大到多少、有沒有 `callerTimedOut: true`。
    - 或用 `createTestBot` 搭配真的 `withMutex`（不要 mock）和有延遲的 `notionPatch` mock，模擬 10 個不同使用者同時 `+1`，確認第幾則開始逾時。

    如果要處理，方向是**合併排隊中的任務（group commit）**：拿到鎖之後，把同一個 key 已經在排隊的任務一次取出，只 refetch 一次，在記憶體裡照順序套用每個任務的計算（照順序套，「額滿只成功一部分」這類判斷才會跟逐筆處理的結果相同），最後只寫一次（零打和請假是同一頁的兩個欄位，可以併成一次 PATCH），再各自回傳結果。N 個任務的佔鎖時間會從 N×1 秒左右縮到 1～1.5 秒。陷阱：
    - 現在的 mutation 是各 handler 傳給 `withFreshCalendarEvent` 的閉包，每個都自己讀、自己寫。要改成「讀一次 → 純函式套用 → 寫一次」，會動到報名／請假的核心邏輯，要寫 ADR，也要用預設模型做 code review。
    - 合併的那次寫入失敗的話，整批任務一起失敗，所有人都會收到「系統錯誤」，失敗的影響範圍變大。
    - 擋不住 43 秒那種卡住的單次寫入（排隊中的照樣逾時），只能讓卡住結束後的積壓一次清空，不再拖累下一輪（43 秒那次，第二輪的 `waitMs` 11～13 秒就是被積壓拖到的）。
    - 合併之後，號碼牌閘門（[ADR 0018](adr/0018-entry-gate-orders-lock-entry.md)）保證的「照收到順序」要在批次內的套用順序維持住，不能因為合併而重排。
    - 不要用拉長 `TIMEOUT_MS` 來替代：理由見上一條的「拉長 mutex 逾時」。
