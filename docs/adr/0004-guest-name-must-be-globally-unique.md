# Guest 名字在同一活動內必須全域唯一，不能只在單次呼叫內唯一

`零打` 欄位（`calendar-repository.ts` 的 `guests`）是 Notion 的 `multi_select` 型別。multi_select 的選項是用**名稱**去重的集合語意：同一個屬性套用兩個名稱完全相同的選項，等同套用同一個選項一次，Notion 伺服器端會把重複名稱靜默合併成一筆，不會報錯、不會有任何跡象顯示「有一筆被吃掉了」。這跟 `relation`／`people` 這類允許同一個 id 重複出現的屬性型別不同，是 `multi_select` 本身的資料結構決定的。

**這代表任何組出 `guests` 陣列、準備整包 PATCH 回 Notion 的程式碼，都必須保證陣列裡每個字串在「這個活動當下的完整清單」裡是唯一的**，不能只保證「這次呼叫新增的幾筆彼此不重複」——因為 `calculateAddCapacity`（`src/commands/registration/capacity-calculator.ts`）算出的新條目，最終會跟 `event.guests`（前面已經寫進 Notion 的既有內容）合併成一個陣列整包寫回，如果新條目剛好跟既有內容同名，一樣會在 Notion 端被吃掉。

**2026-09-17 正式環境實際發生過**：季租成員連續 4 次 `@Dobby +1`，因為當時的命名邏輯每次呼叫都從編號 0 重算（沒有先掃描 `event.guests` 已經用到哪些編號），4 次呼叫產生了 4 個一模一樣的字串「XX的朋友」，Notion 端只留下 1 筆，其餘 3 次報名被無聲遺失，程式端全程沒有任何錯誤或警告，使用者也收到「報名成功」的回覆。修法是 `findMaxExistingIndex`：新增條目前先掃描 `event.guests` 找出這個人目前已經用到的最大編號，從那之後接續編號（見 `docs/code-review-2026-09-17.md` 第 4.3 節）。同時加了一層防禦性檢查：組出最終陣列前偵測有沒有重複字串，若有就記 `logger.warn`（含完整清單），不阻擋寫入，但至少留下可以事後排查的線索。

新增任何會寫入 `零打`（或未來其他 multi_select 欄位）的程式碼路徑時，記得這個約束：**寫入前的完整陣列必須自我去重過**，不能假設「我這次加的東西跟之前的東西一定不會撞名」。如果撞名，不會有任何錯誤訊息，只會在使用者完全沒發現的情況下悄悄少一筆資料。
