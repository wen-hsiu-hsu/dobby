# 報名／請假逾時後，成員用 `@Dobby next` 自己確認結果

2026-10-04 測試環境一次 Notion PATCH 卡了 43 秒，排在後面的 7 則報名／請假全部收到「處理時間較長，這次操作可能已經完成，請勿重複操作。如需確認，請洽管理員。」（經過見 `docs/performance-observations.md` 的 43 秒寫入那條）。資料沒錯，問題是使用者**沒有任何方法自己確認結果**：

- replyToken 已經被逾時訊息用掉，bot 也不用 push 補發（`CLAUDE.md`）。
- 群組裡沒有「輸入中」動畫，不能讓使用者乾等真正的結果。
- 唯一能看目前名單的 `@Dobby next` 只限管理員使用。這個限制是從 n8n 遷移時就有的，沒有文件記錄原因；卡片上的三顆按鈕本來就只作用在操作者自己身上。

卡住的寫入本身擋不住：中斷或重送 PATCH 都不安全，因為 Notion 沒有條件式寫入或冪等鍵。那次 PATCH 的回應帶的 `last_edited_time` 是 09:46（UTC），但回應 09:47:06 才到，表示寫入在回應前至少 7 秒就已經生效。所以這次決定把「結果不明」改成「可以查證」。

## 決定

1. **`@Dobby next` 開放給所有成員。** 指令清單卡把「本週打球資訊」從管理員專用區移到查詢區。
2. **`next` 讀取時，如果同一個活動日期還有報名／請假沒跑完，卡片後面另附一則文字提醒**：「⏳ 還有 N 筆報名／請假正在處理，上面的名單可能還會變動，請稍後再查一次，不要重複操作。」N 來自 `pendingTaskCount(date)`（`src/services/mutex.ts`），也就是 `withMutex` 原本只用來記 log 的 `inFlight` 計數：排隊中與執行中的任務都算，呼叫端已經逾時、還在背景跑的也算。
3. **逾時訊息分成兩種**（`with-fresh-calendar-event.ts`，依 `MutexTimeoutError.started` 判斷），兩種都叫使用者不要重送，也都引導到 `@Dobby next`：
    - 已經開始：「處理時間較長，這次操作可能已經完成，請勿重複操作。…」，寫入可能已經生效、也可能還在送，結果真的不知道。
    - 還在排隊：「前面的操作處理較久，這次操作已排隊，會依序處理，請勿重複操作。…」。排隊中的任務不會被取消（[ADR 0002](0002-mutex-timeout-does-not-cancel-task.md)「例外」、[ADR 0018](0018-entry-gate-orders-lock-entry.md)），一定會執行，所以可以講得比「可能已完成」更確定。但不能說「已完成」，也不能預告結果（例如輪到時已經額滿）。

## 不要改成的寫法

- **提醒不要放進卡片裡。** `next` 必須跟週報推播輸出完全相同的卡片（[ADR 0011](0011-weekly-status-flex-card.md)），所以提醒是另一則 text 訊息，卡片本身不動。
- **`next` 不要為了拿到「最新」結果而進鎖。** 它是唯讀的。進鎖的話，Notion 寫入卡住時它也會跟著排隊、逾時，正好在使用者最需要確認的時候失效。不進鎖就可能讀到寫入前的狀態，所以才要有第 2 點的提醒。沒有提醒的話，使用者看到名單上沒有自己，就會重送不冪等的 `+1`。
- **計數取讀取前後的較大值。** 讀取前就在排隊的任務，可能在讀取途中完成，讀到的名單不一定有反映；讀取途中才進來的任務，讀到的名單一定沒有。只看其中一個時間點，都會漏掉其中一種情況。
- **`pendingTaskCount` 只用來顯示提醒，不能拿來決定要不要進鎖或寫入。** 它是快照，讀完的下一刻就可能變了。
- 進鎖前（查 USERS、`resolveTarget`＋季資料，以及號碼牌閘門等待）、還沒呼叫 `withMutex` 的任務不會算進去。這不影響收到逾時訊息的人：逾時只會在 `withMutex` 裡發生，所以他照訊息去下 `next` 時，自己那筆一定已經算在 N 裡，直到真正寫完。其他人的任務也只會短暫沒算到：閘門最多只等 5 秒，前一號一呼叫 `withMutex` 就放行下一號，所以 Notion 寫入卡住時，排在後面的任務很快就都會進到 mutex 佇列。
