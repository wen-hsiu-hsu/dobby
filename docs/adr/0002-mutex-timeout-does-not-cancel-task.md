# withMutex 逾時只影響呼叫端等待，不會取消已開始的背景任務

`src/services/mutex.ts` 的 `withMutex(key, fn)` 對同一個 key 的呼叫做 FIFO 排隊，確保報名/請假這類「讀取 → 計算 → 寫回」Notion 的操作互斥。每次呼叫有 10 秒逾時，從呼叫 `withMutex` 那一刻起算，**包含排隊等前一個任務的時間**，不是只算 `fn()` 本身。逾時**不會**讓已經開始的 `fn()` 停止執行——它只影響「這次呼叫的呼叫端等多久」，`fn()` 仍在背景跑到真正完成，佇列裡下一個排隊的呼叫也會等到它真正完成才開始，不會因為呼叫端逾時就提早搶跑。逾時當下還在排隊、`fn()` 還沒開始的任務，預設之後也會照常執行；呼叫端傳了 `{ cancelIfNotStarted: true }` 才會直接跳過（見下方「例外：還沒開始的任務可以取消」）。

**呼叫端收到 `MutexTimeoutError` 時，不能當成操作失敗回覆使用者。** `fn()` 之後仍可能寫入成功，但呼叫端已經用 replyToken 回了訊息，之後不可能再補發真正的結果（token 只能用一次，也不用 push 補發），使用者只會看到這則訊息。（2026-10-04 以前回覆是在 `fn()` 裡送的，會被 LINE 拒絕；之後改在鎖外送，逾時就直接不送。）報名 `+N`／`-N` 不是冪等的，使用者看到「系統錯誤」而重試，就會重複報名或多取消一筆。所以 `withFreshCalendarEvent` 收到 `MutexTimeoutError` 時另外回覆「這次操作可能已經完成，請勿重複操作」，不回「系統錯誤」。逾時當下還在排隊的任務也一樣：報名／請假不取消排隊中的任務（見下方「例外」），它之後還是會執行。

**為什麼不改成從拿到鎖才開始計時**：`notion-fetch.ts` 的 `fetch` 沒有請求逾時。若計時只從拿到鎖開始，前一個任務卡住時，排隊的人永遠拿不到鎖、永遠收不到回覆，等於拿掉現有唯一的安全網。要改的話，得先補上 fetch 逾時或總等待上限。

實作上把兩件事拆開：`settle`（真正執行 `fn()` 的 promise，只依賴「上一個 `settle` 真的完成」，永遠不被逾時打斷，佇列鏈永遠掛在它上面）跟呼叫端拿到的 promise（`Promise.race([settle, timeout])` 的結果）。**`queues` 這個 Map 的清理邏輯必須綁在 `settle` 真正完成上，不能綁在「還有幾個呼叫者在等」的計數上**——後者會因為呼叫者逾時而提前歸零，若這時把 `queues` 的 entry 清掉，下一個全新呼叫會讀到「沒有人在排隊」，跳過還在背景跑的舊任務直接搶跑，重新引入本來要防的 race，只是延後觸發、更難重現。清理時還要先確認 `queues.get(key) === tail` 才刪：A 結束時，entry 可能已經換成排在後面、還在跑的 B，無條件刪除會讓 B 執行期間進來的新呼叫不等 B 就開跑（`mutex.test.ts` 有測這個時序）。

**`Mutex task finished` 摘要 log 掛在 `tail` 完成處，不掛在呼叫端的 `finally`**：理由跟 `queues` 清理一樣。逾時後呼叫端的 `finally` 早就跑完，但 `fn()` 還在背景持有鎖，在 `finally` 記會把 `heldMs` 量短、`callerTimedOut` 的案例正好是最需要準確數字的時候。同理，`queuedAhead` 用的計數（`inFlight`）只在 `tail` 完成時才減一，不在呼叫端的 `finally`，否則會漏算呼叫端已逾時、但還在背景跑的任務。摘要在 `void tail.then(...)` 裡寫出時，AsyncLocalStorage 保留的是**註冊 `.then` 時**（也就是呼叫 `withMutex` 的那個請求）的 context，所以 reqId 仍是原本事件的，即使 `fn()` 是被別的請求的程式碼觸發完成（`mutex.test.ts` 有測）。

**沒有「這把鎖現在有沒有人在用」的查詢函式，也不要加回來。** 以前有一個 `isLocked()`，讀的是另一個在呼叫端 `finally` 減一的計數（`pending`），也就是「還有沒有呼叫端在等」，不是「背景還有沒有任務在寫」。`trackUser` 曾用它決定要不要信任呼叫端的 USERS 快照，在逾時情境下就信任了過時的快照。2026-10-04 `trackUser` 改成鎖內一律重讀（[ADR 0017](0017-track-user-always-rereads-inside-lock.md)）之後，`isLocked()` 和 `pending` 已經沒有正式程式在用，就一起刪掉了，避免下一個人再拿它判斷資料是否新鮮。需要「拿到最新資料」時，在鎖內重讀。

**例外：還沒開始的任務可以取消（`cancelIfNotStarted`，2026-10-04 加入）。** 上面「不能取消」的理由只對已經開始的任務成立；還在排隊、`fn()` 沒跑過的任務根本還沒送出任何請求，跳過它不會有資料問題。觸發的事件（2026-10-04 測試環境）：一次 PATCH 卡 43 秒，後面排隊的 7 則全部收到「可能已完成」，又在 30～40 秒後默默寫入，使用者完全不知道結果。當時 `withFreshCalendarEvent` 改傳 `cancelIfNotStarted`，逾時時還在排隊的任務永遠不會執行，回覆「目前處理較慢，這次操作沒有執行，請稍後再送一次」。

**同一天，報名／請假又撤掉取消，目前沒有呼叫端開這個選項。** 取消會破壞「先送先報」（[ADR 0018](0018-entry-gate-orders-lock-entry.md)）：Notion 寫入卡住時，最早排隊的人逾時點最早，最先被取消，後送的人反而照常執行。只保留 `-N`／`假`／`銷假` 的取消也不行，因為它們會改變後面的人拿不拿得到名額：C 的 `-1` 被取消，排在它後面的 A 的 `+1` 就拿到「名額不足」，C 重送後空出的名額被更晚的 D 拿走；`銷假` 被取消，後面的 `+N` 就拿到原本不該有的名額。社團的要求是先送先報優先，明確的回覆其次，所以接受 43 秒事件那種「可能已完成、看不到結果」的體驗。這個選項和下面的保證都還留在 `mutex.ts`，也有測試；之後有「被跳過時會明確告訴使用者、而且跳過不影響別人結果」的呼叫端，可以再開。

- **怎麼保證「沒開始」就真的不會跑**：`MutexTimeoutError.started` 在 timer 觸發的當下，同步讀 `startedAt` 決定，`cancelled` 則是 `started` 為 false 且有傳 `cancelIfNotStarted`；`settle` 輪到時，也在同一個同步步驟裡先檢查 `callerTimedOut`、再設定 `startedAt`、再呼叫 `fn()`。JS 是單執行緒，兩者只會有一個先跑：timer 先觸發，任務就永遠被跳過；`fn()` 先開始，timer 就會回報 `started: true`。不會有「告訴使用者沒執行，結果又跑了」的空窗。要回覆「沒有執行」的呼叫端，要看 `cancelled`，不是 `!started`：「確定不會執行」由 mutex 決定，之後如果有人拿掉選項或照抄到沒開選項的呼叫端，也不會誤回「沒有執行」（2026-10-04 撤掉取消之前，`withFreshCalendarEvent` 就是這樣判斷的）。
- **被跳過的任務仍佔佇列位置到輪到它為止**：它的 `settle` 會在前一個任務真正結束後才 reject（內部的 `MutexCancelledError`，不會傳到呼叫端），佇列鏈、`inFlight` 計數、`Mutex task finished` 摘要都照一般任務的時序處理，摘要帶 `cancelled: true`、`heldMs: 0`、`fnFailed: false`。後面的任務因此只多等幾個 microtask（同一個 tick 內），不會跳過還在跑的前一個任務。
- **為什麼是 opt-in，不是預設**：`user-management.ts` 的 `trackUser` 也用 `withMutex`，它寫的 `message_counts` 是累加值，佇列慢就丟掉會漏算發言數，也沒有人會被告知。只有「被跳過時會明確告訴使用者」的呼叫端才該開；報名／請假雖然會告訴使用者，但跳過會改變別人的結果，所以也不開（見上方）。
- **只取消排隊中的任務，不擋 refetch 之後、PATCH 之前那段**：報名／請假的 mutation 都只寫一次，理論上可以在寫入前再檢查一次逾時旗標，把「可能已完成」縮到只剩 PATCH 正在送的情況；但那段窗口只有一次 refetch（約 0.4 秒），效益太小，沒做。

**為什麼不讓逾時真的取消已開始的 `fn()`**：Notion 沒有提供半途中止一個已送出的 PATCH 請求的機制，「取消」頂多是「呼叫端不再等待這個 Promise 的結果」，底層的 HTTP 請求跟 Notion 端的資料寫入已經送出去了，無法真的撤回。與其假裝取消、卻讓底層仍在寫入的資料跟後面排隊的操作互相覆蓋，不如老實承認「逾時只是呼叫端放棄等待」，並確保佇列的正確性建立在「真正完成」而非「呼叫端還在不在乎」之上。

新增或修改 `withMutex` 相關程式碼時，若發現逾時邏輯又被改回「逾時就讓下一個排隊任務開始」，就是在重新引入 2026-09-17 分模組程式碼審查時發現、並在同一天修掉的這個 race（詳見 `docs/code-review-2026-09-17.md` 第 4.1 節）。這個問題是審查時發現、修復時確認會造成「後到的請求讀到舊資料搶先寫入、逾時前的舊寫入事後又覆蓋回去」的資料遺失，但在正式環境尚未實際觀測到因此發生的事故——不要把它跟同一天另一個真的在正式環境造成資料遺失的 guest 命名重複問題（見 `docs/adr/0004-guest-name-must-be-globally-unique.md`）搞混。
