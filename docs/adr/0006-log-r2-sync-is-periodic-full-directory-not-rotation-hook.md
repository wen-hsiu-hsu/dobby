# Log 同步到 R2 是「週期性重傳整個目錄」，不是掛 pino-roll 的輪替事件

Dobby 準備部署到 Zeabur 這類容器檔案系統是 ephemeral 的平台，每次重啟/重新部署 `logs/` 資料夾會被清空，本機 7 天保留機制（`src/utils/log-cleanup.ts`）完全保不住跨重啟的 log 歷史。這份 ADR 記錄 `src/utils/log-upload.ts` 把 log 檔案備份到 Cloudflare R2（S3 相容物件儲存）的實作，選了「週期性掃整個 `logs/` 目錄、全部檔案重傳一次」，而不是幾個看起來更精巧的替代方案。

**為什麼不掛 `pino-roll` 的輪替事件，等某個檔案「輪替完成」才傳**：`pino-roll` 只 emit `write`/`error`/`cleanup-complete` 這幾種事件，沒有「這個檔案已經輪完、之後不會再被寫入」這種事件可以監聽。理論上可以用 `frequency: 'daily'` 加上「昨天的檔案應該已經穩定」這種時間推論去猜哪個檔案輪完了，但那是脆弱的猜測（跨日邊界、服務重啟時間點都可能讓猜測失準），不如直接放棄找輪替完成的訊號。

**為什麼是「全目錄週期性重傳」而不是「只傳新完成的檔案」**：只傳新檔案聽起來更省頻寬，但要先解決「怎麼知道一個檔案已經傳過」——維護一份已上傳清單（存在記憶體會在重啟時遺失、存在 Notion 或另一個檔案又多一層依賴跟failure mode）。而且更關鍵的是，ephemeral 檔案系統的風險場景剛好是「今天正在寫入、還沒輪替完成」的那個檔案在重啟當下遺失——如果同步邏輯只傳「已完成」的檔案，反而漏掉最需要保護的那份。全目錄週期性重傳把這兩個問題一起解決：不管檔案是否輪替完成，每 `R2_LOG_SYNC_INTERVAL_MINUTES`（預設 15 分鐘）就把 `logs/` 底下所有 `.log` 檔案全部 PUT 一次到 R2 同一個 key（`logs/<prefix>/<原始檔名>`）。同一個 key 反覆覆寫讓邏輯天生冪等——不用維護任何「這個檔案傳到哪了」的狀態，程式碼因此簡單很多；代價是每次都整份重傳而不是只傳增量，但 log 檔案本身不大、15 分鐘一次的頻率，這個代價可以接受。（註：現在已改成以檔案為單位跳過沒變動的檔案，見文末「以檔案為單位的變動偵測」。）

**為什麼選 R2 而不是其他物件儲存**：R2 是 S3 相容 API，換供應商（換回 AWS S3、或其他相容服務）成本低，不會被單一雲商綁死；R2 沒有 egress 費用，log 檔案這種「寫多讀少、大部分時間躺著不動、真的要讀通常是整批拉出來查」的資料型態特別適合；免費額度（10GB 儲存、每月 100 萬次 Class A 操作、1000 萬次 Class B 操作，每月重置，非試用）也遠遠超過這個規模的 log 檔案。

**為什麼失敗不做額外的 retry/backoff**：`uploadAllLogs()` 裡每個檔案各自 try/catch，一個檔案失敗不影響其他檔案繼續上傳（比照 `display-name-update.ts` isolate per-item failure 的先例），但失敗的檔案本身不會在同一次執行內重試。這不是漏掉了，而是因為週期性同步本身就是天然的重試機制——這次傳失敗，反正同一個檔案 15 分鐘後還會被同一套邏輯再傳一次（同一個 key，覆寫語意），不需要在單次執行內再疊一層 retry/backoff 增加複雜度。真正需要人介入的只有「持續好幾個週期都失敗」這種情況，`/logs` 頁面的 R2 同步狀態徽章（琥珀色「失敗，等待下次重試」）就是為了讓這種情況被看見。

**為什麼 `/logs` 的 R2 同步狀態徽章不借用既有事件時間軸的「完成／降級／警告／失敗」機制**：事件時間軸（`docs/logging.md`）的每一張卡片對應一個 `reqId`——一次 LINE 事件處理、一次排程執行。R2 同步狀態不是這樣的東西：它是「目前」這個服務對 R2 的健康狀態，是跨越所有執行、只看「最近一次成功/失敗發生在什麼時候」的全域狀態，語意上不屬於任何單一 reqId 或事件。硬要塞進事件時間軸（例如把每次 `uploadAllLogs()` 執行都當成一個「排程」事件列出來）會製造出大量同質、對日常使用沒有價值的卡片（預設 15 分鐘跑一次，一天就接近一百筆），而且回答不了真正該問的問題：「現在」R2 備份有沒有在正常運作。所以另外用 `getR2SyncStatus()` 維護一組模組層級的 `lastSuccessAt`/`lastFailureAt`/`lastFailureMessage`（模式比照 `logger.ts` 的 `getLogLevel()`），直接放在 header 當一個獨立徽章，跟 LOG_LEVEL 徽章並列，而不是進事件列表。這兩個時間戳互不清空——這次失敗不會把上次的 `lastSuccessAt` 清掉，反之亦然——讓徽章邏輯可以單純比較兩者的新舊來判斷「目前」是不是正常。

不過 `uploadAllLogs()` 整次執行仍然用 `runWithContext` 包住（跟 `weekly-push.ts`/`display-name-update.ts` 一樣），所以底層真的想追某一次同步跑了什麼（例如診斷「為什麼這次失敗」），還是找得到對應的 reqId、在事件時間軸的「排程」分頁看到那次執行的完整過程——徽章只是不把它當成使用者平常會想逐筆瀏覽的「事件」。

沒設定 R2 時（`isR2Enabled()` 在模組載入時就算好，執行期間不會變），`startLogUpload()` 直接不排程，只在 `runWithContext` 外面記一行 debug（`R2 not configured, log sync disabled`，沒有 reqId，在 `/logs` 只會是一筆「系統」事件）；`uploadAllLogs()` 本身則靜默 return，避免每個週期或 graceful shutdown 都在事件時間軸多出一張沒有意義的「排程」卡片。

## 以檔案為單位的變動偵測（後續修改）

原本每一輪都把 `logs/` 底下所有 `.log` 整份重新 PUT。本機保留 7 天，每輪大約傳 7～8 個檔案，但其中已經輪替完的舊檔內容根本不會再變，每 15 分鐘重傳一次純屬浪費。所以後來改成：`log-upload.ts` 在記憶體裡維護一個 `Map<檔名, { mtimeMs, size }>`，記錄每個檔案「上次成功上傳時」的狀態；每輪先對每個檔案 `stat`，`mtimeMs` 跟 `size` 都和記錄相同就跳過，只上傳有變動的檔案。

**這跟上面「不維護已上傳清單」的理由不衝突**：當初拒絕已上傳清單，是因為「存在記憶體會在重啟時遺失、存在外部又多一層依賴」——擔心的是狀態遺失會造成漏傳。這份 Map 刻意只存在記憶體，但它的失效方向是安全的：重啟後 Map 是空的，第一輪就退回原本的全量重傳；上傳仍然是對同一個 key 覆寫，冪等性不變。它只是「跳過確定沒變的檔案」的最佳化，不是「判斷哪些檔案還沒傳過」的依據，所以狀態遺失的代價只是多傳一輪，不會漏掉任何檔案。其他細節：

- Map 只在上傳**成功後**才寫入，而且寫入的是上傳**前** `stat` 拿到的值。上傳失敗不更新，下一輪自然重試（跟上面「週期性同步本身就是重試機制」一致）；`stat` 之後、讀檔之前如果檔案又被寫入，實際傳上去的內容比記錄新，下一輪 `stat` 值不同會再傳一次，只會多傳、不會漏。
- 單一檔案 `stat` 失敗比照上傳失敗處理：算失敗、記 warn、繼續處理下一個檔案。
- 已經不在目錄裡的檔名（被 `log-cleanup.ts` 刪掉的）每輪會從 Map 移除，避免 Map 無限長大；同名檔案之後再出現會被當成新檔重傳。
- 整輪沒有任何失敗就更新徽章的 `lastSuccessAt`，**包括全部檔案都沒變動、一個都沒上傳的情況**——否則閒置時徽章的「成功」時間會停在最後一次有新 log 的時候，看起來像同步停擺。

**完成訊息 `R2 log sync complete` 必須是 debug，不能是 info**，原因有兩個：

1. **自我觸發變動**：正式環境 `LOG_LEVEL=info`，如果這行是 info，它本身就會寫進今天的 log 檔，下一輪今天的檔案 `mtime`/`size` 一定變了，變動偵測等於自己觸發自己。降成 debug 後正式環境不會寫進檔案。（開發環境 `LOG_LEVEL=debug` 仍會寫進檔案，所以開發環境今天的檔案每輪都會重傳，這可以接受。）
2. **卡片洗版**：這行在 `runWithContext` 裡（有 reqId），是 info 的話正式環境的 `/logs` 每 15 分鐘就會冒出一張背景作業卡片，正是上面徽章段落想避免的情況。

真的要追某一輪同步的細節，把 `LOG_LEVEL` 調成 debug 就看得到（帶 `succeeded`/`skipped`/`failed`/`total`）；個別檔案失敗的 warn 不受影響，正式環境一樣會記錄。
