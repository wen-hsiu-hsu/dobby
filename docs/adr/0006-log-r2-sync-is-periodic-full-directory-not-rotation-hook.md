# Log 同步到 R2 是「週期性重傳整個目錄」，不是掛 pino-roll 的輪替事件

Dobby 準備部署到 Zeabur 這類容器檔案系統是 ephemeral 的平台，每次重啟/重新部署 `logs/` 資料夾會被清空，本機 7 天保留機制（`src/utils/log-cleanup.ts`）完全保不住跨重啟的 log 歷史。這份 ADR 記錄 `src/utils/log-upload.ts` 把 log 檔案備份到 Cloudflare R2（S3 相容物件儲存）的實作，選了「週期性掃整個 `logs/` 目錄、全部檔案重傳一次」，而不是幾個看起來更精巧的替代方案。

**為什麼不掛 `pino-roll` 的輪替事件，等某個檔案「輪替完成」才傳**：`pino-roll` 只 emit `write`/`error`/`cleanup-complete` 這幾種事件，沒有「這個檔案已經輪完、之後不會再被寫入」這種事件可以監聽。理論上可以用 `frequency: 'daily'` 加上「昨天的檔案應該已經穩定」這種時間推論去猜哪個檔案輪完了，但那是脆弱的猜測（跨日邊界、服務重啟時間點都可能讓猜測失準），不如直接放棄找輪替完成的訊號。

**為什麼是「全目錄週期性重傳」而不是「只傳新完成的檔案」**：只傳新檔案聽起來更省頻寬，但要先解決「怎麼知道一個檔案已經傳過」——維護一份已上傳清單（存在記憶體會在重啟時遺失、存在 Notion 或另一個檔案又多一層依賴跟failure mode）。而且更關鍵的是，ephemeral 檔案系統的風險場景剛好是「今天正在寫入、還沒輪替完成」的那個檔案在重啟當下遺失——如果同步邏輯只傳「已完成」的檔案，反而漏掉最需要保護的那份。全目錄週期性重傳把這兩個問題一起解決：不管檔案是否輪替完成，每 `R2_LOG_SYNC_INTERVAL_MINUTES`（預設 15 分鐘）就把 `logs/` 底下所有 `.log` 檔案全部 PUT 一次到 R2 同一個 key（`logs/<prefix>/<原始檔名>`）。同一個 key 反覆覆寫讓邏輯天生冪等——不用維護任何「這個檔案傳到哪了」的狀態，程式碼因此簡單很多；代價是每次都整份重傳而不是只傳增量，但 log 檔案本身不大、15 分鐘一次的頻率，這個代價可以接受。

**為什麼選 R2 而不是其他物件儲存**：R2 是 S3 相容 API，換供應商（換回 AWS S3、或其他相容服務）成本低，不會被單一雲商綁死；R2 沒有 egress 費用，log 檔案這種「寫多讀少、大部分時間躺著不動、真的要讀通常是整批拉出來查」的資料型態特別適合；免費額度（10GB 儲存、每月 100 萬次 Class A 操作、1000 萬次 Class B 操作，每月重置，非試用）也遠遠超過這個規模的 log 檔案。

**為什麼失敗不做額外的 retry/backoff**：`uploadAllLogs()` 裡每個檔案各自 try/catch，一個檔案失敗不影響其他檔案繼續上傳（比照 `display-name-update.ts` isolate per-item failure 的先例），但失敗的檔案本身不會在同一次執行內重試。這不是漏掉了，而是因為週期性同步本身就是天然的重試機制——這次傳失敗，反正同一個檔案 15 分鐘後還會被同一套邏輯再傳一次（同一個 key，覆寫語意），不需要在單次執行內再疊一層 retry/backoff 增加複雜度。真正需要人介入的只有「持續好幾個週期都失敗」這種情況，`/logs` 頁面的 R2 同步狀態徽章（琥珀色「失敗，等待下次重試」）就是為了讓這種情況被看見。

**為什麼 `/logs` 的 R2 同步狀態徽章不借用既有事件時間軸的「完成／降級／警告／失敗」機制**：事件時間軸（`docs/logging.md`）的每一張卡片對應一個 `reqId`——一次 LINE 事件處理、一次排程執行。R2 同步狀態不是這樣的東西：它是「目前」這個服務對 R2 的健康狀態，是跨越所有執行、只看「最近一次成功/失敗發生在什麼時候」的全域狀態，語意上不屬於任何單一 reqId 或事件。硬要塞進事件時間軸（例如把每次 `uploadAllLogs()` 執行都當成一個「排程」事件列出來）會製造出大量同質、對日常使用沒有價值的卡片（預設 15 分鐘跑一次，一天就接近一百筆），而且回答不了真正該問的問題：「現在」R2 備份有沒有在正常運作。所以另外用 `getR2SyncStatus()` 維護一組模組層級的 `lastSuccessAt`/`lastFailureAt`/`lastFailureMessage`（模式比照 `logger.ts` 的 `getLogLevel()`），直接放在 header 當一個獨立徽章，跟 LOG_LEVEL 徽章並列，而不是進事件列表。這兩個時間戳互不清空——這次失敗不會把上次的 `lastSuccessAt` 清掉，反之亦然——讓徽章邏輯可以單純比較兩者的新舊來判斷「目前」是不是正常。

不過 `uploadAllLogs()` 整次執行仍然用 `runWithContext` 包住（跟 `weekly-push.ts`/`display-name-update.ts` 一樣），所以底層真的想追某一次同步跑了什麼（例如診斷「為什麼這次失敗」），還是找得到對應的 reqId、在事件時間軸的「排程」分頁看到那次執行的完整過程——徽章只是不把它當成使用者平常會想逐筆瀏覽的「事件」。
